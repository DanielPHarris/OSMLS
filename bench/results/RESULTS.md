# Listing changes: measured throughput, latency and lock wait

Run on 2026-11-21 by `pnpm measure`. Every figure below is from this one run on this one machine.

## Machine

- Processor: Apple M1 Max, 10 cores. Memory: 64 GB. System: Darwin 24.1.0 arm64. Node.js v22.21.0.
- PostgreSQL 17.12 (Debian 17.12-1.pgdg13+1): shared_buffers 128MB, synchronous_commit on, fsync on, max_connections 100.
- PostgreSQL ran in Docker Desktop on the same machine, on the laptop's internal solid-state storage.
- The benchmark, the application's code and the database all ran on this machine.

## Dataset and method

- A synthetic benchmark dataset: 10000 listings, 200 agents, 20 offices. It is not a model of any MLS.
- Each run: a copy of the same dataset, 5 seconds of warm-up that is not counted, then 20 seconds measured. Each level was run 3 times.
- Writers call the application's own functions for changing and entering listings. Each price-change writer has listings of its own.
- The pool is the number of database connections the writers share. The application ships with 10.
- Lock wait is the time a change waited for the history lock, recorded by a trigger that exists only in the benchmark's database.

## Instrument check

A price change was seen waiting for the history lock, which was then held for 500 ms. The wait recorded for it was 507.3 ms.

## What the lock timing itself costs

One writer changing prices, pool 10: 241 (224 to 249) a second without the timing, 228 (227 to 231) with it (median, lowest to highest of 3).

This is an estimate of the timing's cost with one writer. It is not a correction for the other results: the record is written while the lock is held, and work done while holding the lock can lengthen the queue behind it under load.
